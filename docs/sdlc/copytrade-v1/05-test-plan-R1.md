## Run summary
63 tests collected: 30 fail, 33 pass (targeted run only, never the full suite). Every failure is an assertion failure on behaviour (no import, collection or fixture errors, no stubs needed). The 33 passing tests are regression pins of behaviour that already works (fixture parsing, optional fields, no-secret logging, no failure record on success, light-wallet error isolation, a light wallet "stays done"), plus boundary cases that must keep working (99,000 fills is not too active; an exactly-at-minimum account value is kept; unreadable accountValue is kept).

## Root cause found while designing (beyond the diagnosis notes)
`runner/wiring.py` gives the scoring REST client a sleeper that never sleeps: a request that does not fit the budget raises `HlBudgetError` at once. The scoring share is 450 weight/min and a full page weighs 120. `Backfiller._collect` is all or nothing, so any wallet needing more than about 3 pages fails midway on the budget and throws its pages away, restarting from the window start for ever and keeping the budget busy (H4, probably the real cause; H1 is the page-cap case). The AC4 tests reproduce this with the real client, real budget and the fail-fast sleeper (`test_R1_AC2_a_dropped_wallet_does_not_stop_the_manager...` and AC4 never complete today). Note `scoring.window_days` is 180, not 24 h: the 100,000-fill cap means about 555 fills/day average over the window.

## Pinned decisions (defaults stand until the PM/PO says otherwise)
1. Log contract (standard `extra` fields on the existing events): `backfill_failed` has `wallet`, `status` (int or absent), `error` (message, no URL or body), `error_type`; `backfill_incomplete` has `wallet`, `pages`, `fills`; new event `backfill_too_active` has `wallet`, `reason="too_active"`, `pages`. A 429 error must expose the status too (`HlRateLimitedError` has none today).
2. Countable: the code has NO alert or ledger path for backfill (the manager's alerts/ledger are not reachable from `Backfiller`). I invented none: the stable `event` key, one record per failed attempt, is the count. If the PM wants an alert/ledger record, that is a new channel and needs a decision.
3. Too active = page cap reached without reaching the present, inside the scoring window. Dropped from candidates (backfill completes without it, `inputs()` is None), no retry from `set_candidates` or `refresh` for 24 h (the `_DAY_MS` constant the backfiller already uses; no new config key), then one new bounded attempt. No ESCALATE: no config key needed.
4. Prefilter: only G11 (`gate.min_account_value_usd`, inclusive) and the address half of G13 (`gate.exclude_addresses`) can run on a leaderboard row. Parsed row fields today: none (only `ethAddress`; the row also has `accountValue` and `windowPerformances` pnl/roi/vlm, which C1 forbids as score inputs, and which no gate reads). Not runnable without fills/state/role: G1-G10, G12, G14, G15 and the role half of G13. Prefilter runs on all rows in served order, then `candidates_k` takes the first k survivors. Missing/unreadable `accountValue` keeps the row. The row value is self-reported; it only saves a fetch, never scores or admits a wallet (C1 intact). The source of the row data is `LeaderboardSource.fetch()` bytes; whether `wallets_in_leaderboard` is extended or a sibling function is added is the developer's choice.
5. Fairness: at most 3 fill pages of one wallet per `step()` (what fits one minute of the 450 weight scoring share); the partial progress (cursor and fills) of an unfinished wallet is kept across steps and failures; its pages count toward the 50-page cap in total; the incomplete wallet blocks `complete` until finished or dropped.
6. Cooldown after a persistent 429 = `hl.backoff_max_s` (existing key) of the injected clock.
